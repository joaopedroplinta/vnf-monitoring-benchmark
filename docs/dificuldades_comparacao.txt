DIFICULDADES NA COMPARAÇÃO eBPF vs sysstat vs Prometheus
==========================================================
TCC — Gerenciamento e Monitoramento de Rede
Data: 2026-04-14

----------------------------------------------------------
1. MEDIÇÃO DE LATÊNCIA DO eBPF IGUAL À DOS OUTROS
----------------------------------------------------------
O maior diferencial teórico do eBPF seria medir latência no kernel.
Porém, o kprobe udp_recvmsg não dispara no kernel 6.12+, forçando
a medição a ser feita no userspace via time.time() — exatamente o
mesmo mecanismo usado pelo sysstat e pelo Prometheus.

Resultado: a métrica principal da comparação (latência de monitoramento)
é calculada da mesma forma nas três ferramentas, o que reduz o
diferencial esperado do eBPF.

----------------------------------------------------------
2. BYTES TX COMPLETAMENTE INCONSISTENTE
----------------------------------------------------------
Valores registrados na última execução (60s):

  eBPF:       767 bytes
  sysstat:    ~122 MB
  Prometheus: ~122 MB

O eBPF conta apenas os bytes que o WAF envia como resposta
(tcp_sendmsg com sport=8080), que são strings curtas como
"BLOCKED:SQLi\n" ou "ALLOWED:OK\n".

Sysstat e Prometheus leem /proc/net/dev na interface lo, onde
TX é espelho do RX (no loopback todo pacote enviado também aparece
como recebido). As três ferramentas medem coisas diferentes,
tornando a comparação direta de bytes_tx inválida.

----------------------------------------------------------
3. BYTES RX: LOOPBACK DUPLICA OS DADOS NO sysstat/Prometheus
----------------------------------------------------------
Na interface lo, quando o cliente envia um payload para o WAF,
esse tráfego aparece tanto no RX quanto no TX da interface.
Sysstat e Prometheus contam o tráfego total do loopback,
não apenas o que o WAF processou.

O eBPF com filtro sport=8080 isola apenas o lado servidor,
sendo conceitualmente mais preciso — mas isso impede a comparação
direta dos valores numéricos entre as ferramentas.

----------------------------------------------------------
4. eBPF REQUER PRIVILÉGIOS ELEVADOS
----------------------------------------------------------
O coletor eBPF exige:
  - privileged: true no container
  - Acesso a /sys/kernel/debug e /sys/fs/bpf
  - Headers do kernel instalados no host
  - PID namespace do host (pid: "host")

Esse overhead de setup e segurança não está refletido nas
métricas coletadas, mas é relevante para a avaliação prática
das ferramentas em ambientes reais.

----------------------------------------------------------
5. CPU DO PROMETHEUS INFLADA
----------------------------------------------------------
Valores de CPU média registrados:

  eBPF:       0.33%
  sysstat:    0.33%
  Prometheus: 0.83%

A diferença provavelmente vem do servidor HTTP mantido ativo
em :8000/metrics, não da coleta de métricas em si. Isso mistura
overhead de monitoramento com overhead de exposição de métricas,
dificultando uma comparação justa do custo de coleta.

----------------------------------------------------------
RESUMO
----------------------------------------------------------
As três ferramentas acabam medindo a latência da mesma forma
(userspace) e medem bytes de formas incompatíveis entre si.
Isso enfraquece a comparação e precisa ser considerado na
análise dos resultados do TCC.
